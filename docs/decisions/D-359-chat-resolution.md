# D-359 — M4: chat resolution wired through the shared derivation (no third binding)

## Status

RATIFIED

## Context

D-337 ratified deterministic-first resolution: exact syntax and known
capability names resolve deterministically; only genuinely ambiguous NL
routes through the existing PROBABILISTIC/realization branch (`resolve.classify@1`,
D-323); every resolution is ledgered. The map's begin order carries the 360
addendum's A2 refinement verbatim: when M4 lands chat resolution, chat
capability names must be generated by the SAME derivation the other surfaces
consult — `docs/SURFACES.md`'s MCP tool-generation rule ("tools are generated
from the booted composition's routed ops, nothing else") — not by a third,
separately-maintained binding. Today that derivation exists only as private
code inside `surfaces/mcp/src/mcp.ts` (`opToToolName`/`buildOpMeta`); the
chat pilot is the third consumer, so the derivation moves to contracts and
the MCP surface becomes an importer — the rule's consumer set extends, no
new registry is invented. D-353 supplies the human principal the
conversation names; D-358 supplies the storage the exchange lands in.

## Options

| Criterion | (a) Shared derivation in contracts + `chat.resolve@1` reusing resolve.classify@1 (recommended) | (b) Third binding inside vivim-chat | (c) Extend resolve.classify@1's input with utterance |
|---|---|---|---|
| A2 / SURFACES rule | One derivation source, three consumers (MCP tools, CLI ops list, chat names) | Exactly the separately-maintained binding A2 forbids | n/a |
| D-337 / D-323 | Deterministic chat half + ledger discipline; realization/human branches are the SHARED classifier's, verbatim — no parallel resolution logic | A forked classifier drifts from D-323's rule table | Reopens a ratified op surface for a chat-only concern |
| Ledger honesty | Every verdict gets a `ResolveDecision` row — chat-originated ones carry buildDecisionRef "D-323" and cite the conversation | Same row shape, wrong authority path | Director-owned ns polluted with chat semantics |

## Decision

**Decision:** (a) Land M4 as wiring, three pieces:

1. **The shared derivation moves to contracts** (`contracts/src/surface.ts`):
   `surfaceOpMeta(manifests)` (owner plugin + declared risk per routed op)
   and `capabilityNamesFromRouted(routedOps)` (the canonical capability-name
   set derived from the booted composition's routed ops, NOTHING else).
   `surfaces/mcp` refactors to import it — `tools/list` and chat resolution
   now consult one definition (the A2 consumer-set extension, verbatim).
2. **`chat.resolve@1` (CONTRACT/READ) in vivim-chat** — the chat pilot's
   resolution op. Input `{conversationId, utterance, capabilities}` —
   `capabilities` is the caller-side output of the shared derivation (the
   same set MCP's `tools/list` would show for this composition; op-grammar
   validated, dup-checked, fail-closed on malformed input). The pure core
   (`chatResolvePure`):
   - **Deterministic half (D-337):** the utterance, trimmed, exactly names a
     passed capability → branch `rule`, kind `DETERMINISTIC`, capability =
     that op (M-Pilot §M4's mapping: exact command / known op name → rule).
     The verdict is ledgered by vivim-chat itself as a `ResolveDecision`
     row (ns `resolve`, rev 1, `buildDecisionRef: "D-323"`, evidenceRefs
     citing the conversation) — the same record shape the director writes,
     with the ns `resolve` writer row extended same-commit.
   - **Ambiguous half (D-337):** no deterministic hit → port call
     `resolve.classify@1 {op: "chat.complete@1"}` — the SHARED classifier
     rules on the chat archetype: a PROMOTED realization yields the
     realization branch (class-mapped kind per D-323 — SIMULATOR maps to
     DETERMINISTIC; the PROBABILISTIC kind arrives with a non-simulator
     class; confidence stays a ranking signal, D-303), no realization yields
     HUMAN with an empty capability (routes NOWHERE by construction). The
     director writes its own decision row; vivim-chat never duplicates it.
   - Resolution ≠ execution: `chat.resolve@1` never invokes the resolved
     capability. The caller executes through the router and reports via
     `resolve.report@1` (rev 2) — the exact director discipline.
3. **Trust posture, stated:** `capabilities` is caller-supplied, derived
   from the booted composition — the same trust level as the root principal
   itself (SURFACES v1 honesty: surfaces ARE root; nothing they pass can
   exceed root authority). A verdict naming an unroutable op fails at
   execution (unknown op REFUSES) — fail-closed downstream, the ledger keeps
   the honest verdict.

## Consequences

- The D-337 pilot obligation is exercisable end-to-end: exact commands
  resolve deterministically (ledgered), one ambiguous utterance routes
  through the shared realization branch (ledgered), unresolvable input
  escalates HUMAN (ledgered) — nothing silent, no parallel classifier.
- The MCP surface's tool list and the chat resolver's capability names
  cannot drift: one derivation, two consumers, enforced by import rather
  than convention.
- ns `resolve` gains a second WRITER (vivim.chat, deterministic chat
  verdicts only) — the `VAULT-NAMESPACES.md` row is extended in the same
  commit; the director remains the sole writer of realization/human verdicts.
- The gate layer is untouched (host 997/1000 stands); `chat.resolve@1` is
  READ (never gate-triggering, outside the D-351 net by construction).
