## 0 · Why this document exists

An audit of the Consolidated Core against the five files (verified by direct
search on 2026-09-20, not by memory) returned a clean split:

- The **constitutional and falsifier core** — the inversion, the NLCP, the
  5-tuple and CP-1..CP-4, the healing loop, the provenance axes, the physics
  gaps, the refusal register, the falsifiers — is covered by the working set,
  and in most places **expanded** (12 → 19 refusals; F1–F7 → F1–F12 + CP;
  the conversation event → the governed event).
- The **program-state, integration, ecosystem, and open-decision content** is
  **not carried**: zero mentions in the working set of the AKB, the S0
  zero-state principle, the capture-vs-READ partition, the 12-axiom continuity
  table, the four kernel planes, the BM25/grep retrieval fork, algo-steering,
  tokenomics, P2P install-sharing, the canvas dev-poc, `vvv`, or the Chrome
  extension relay (all grep-verified).

Both things are true at once because they answer different questions. The five
files answer *what is the end state made of*. The Consolidated Core also
records *where the program actually stands, what integrates with what, and
which forks are open right now*. Atomization intentionally shed that material;
this companion carries it back, indexed, so nothing is lost when the
Consolidated Core eventually ages out.

The fix is deliberately **not** a decision record: the owner direction holds
("not yet at build decisioning"), the repo is parked, and none of this content
is authorized to become D-409 or an amendment on its own. It is working-set
material, traveling with the vision, waiting for decisioning.

### 4.2 · The AKB / legacy integration strategy

The whole track, nowhere in the working set. The Consolidated Core's §10,
carried:

**The Agentic Knowledge Base (AKB / control-plane DB).** Independent evolution
continues now, but the integration direction is already decided:

- **Omega is the sole authority of execution** — signed manifests, capability
  tokens, consent-gated ports. The AKB's knowledge of capabilities, tools,
  engines, its multi-agent orchestration economy, and its LLM-provider routing
  become things Omega *executes* — not a second execution authority.
- Where both systems compete for the same concept (e.g. "provider"
  realization), **Omega's version wins by default**, because it has real tests
  behind it, not a pair to reconcile later.
- The AKB's **relational strictness** (FKs, legality-FSM triggers) survives
  migration natively via the pattern `vivim.vault` already uses: *a plugin
  owning its own private, strict SQLite store behind a capability-gated port —
  never flattened into generic vault blobs.*
- Migration principle: **harvest-the-invariant, not port-the-code.**
- **Four integration gates, none started until all four are met:**
  - **G0** — Omega publishes the vocabulary contract;
  - **G1** — `vivim.providers` registry is built and gated;
  - **G2** — the capability id `port:provider-io.<class>@1` is reserved;
  - **G3** — decision-log entries ratify the contract.
- The AKB's **"core lattice"** (identity / change / capacity / governance
  layers) is a plausible candidate substrate for the Mind Spine's semantic
  index — **a candidate, not a decision-recorded architecture.**

Cross-map: PHY-19/MAC-15 carry the *legacy-tree* ingestion half of this
strategy (airlock, harvested rows, salvage list) but not the AKB half. The
AKB-lattice candidacy feeds OD-3 (§4.9). The G0–G3 gate set has no anchor

### 4.5 · The five-step Forge pipeline ceremony (and vocabulary reconciliation)

The Consolidated Core's flagship interaction — *"Omega, forge this application
in"* — is a named five-step pipeline:

| Step | Op (source vocabulary) | What it does |
|---|---|---|
| 1 · Capture | `forge.capture.init@1` | hashes the target, snapshots it into the vault |
| 2 · Assay | `forge.survey.run@1` | inspects the code, maps seams and dependencies |
| 3 · Propose | `forge.propose.blueprint@1` | emits a blueprint into ns `proposal`; does not touch code yet |
| 4 · Sign & execute | `forge.execute.build@1` | the user reviews and signs; the Forge gains authority to emit |
| 5 · Prove | `forge.proof.conform@1` | runs the forged app against the original snapshot for behavioral parity |

The working set's vocabulary is different — and it is the frozen one:
D-406 froze a 24-op `forge.*` catalog, and MAC-12 maps the healing loop onto
`forge.mine.capture` / `forge.mine.verify` / `forge.mine.diff` /
`forge.survey.run` / `forge.shape.map` / `forge.emit.*` /
`forge.proof.conform` / `forge.proof.refusal` / `forge.tier.promote`.
The five-step ceremony's `forge.capture.init@1`,
`forge.propose.blueprint@1`, and `forge.execute.build@1` are **not** in that
catalog.

Reconciliation, stated so it stops being a silent mismatch: the **pipeline
shape** (capture → assay → propose → sign → prove, with sign-before-execute
and prove-against-snapshot) is the user-facing ceremony and is carried here as
the canonical five-step description; the **op names** are the frozen catalog's,
and any ceremony-to-catalog mapping (or catalog extension, which would be a
decision) is exactly that — a decision for decisioning, not a vocabulary
drift to be absorbed silently. The overlap ops (`forge.survey.run@1`,
`forge.proof.conform@1`) mean the same thing in both vocabularies.

### 4.7 · Where the rest of Vivim lands (adjacent work)

The Consolidated Core's §10 placement of adjacent systems, each item carried:

**Algorithm steering / algo-combat (recommendation governance).** A concrete
instance of the temporal-substrate gap: a long-running, headless,
provider-mediated composition — human-viable action speed, zero trackable
telemetry, single-account execution only — running on the browser-automation
realization tier under watchdog budget (CP-2), never a centralized
multi-account service. Also a direct test of the "no telemetry, no attention
metrics" refusal applied to the user's own algorithmic environment.

**Tokenomics / decentralized provider-protocol registry.** A long-horizon
extension of the promotion ladder: instead of one synthetic mine gating
harvested → generic, a network of independently operated Omega nodes
crowdsources and cross-verifies provider protocols, tokens as the incentive
for discovery and testing. This does not replace the badge system — it is the
badge system at network scale ("proven against N independent nodes").
Unresolved: how a decentralized verification network interacts with the
"no privileged path" refusal — a naive design risks recreating a central
authority as a **validator cartel** (→ OD-8).

**P2P onboarding (QR/NFC install sharing).** The literal mechanism behind "no
cloud account, ever required": a new sovereign node is bootstrapped
peer-to-peer, not through a login server; sharer/installer roles and the
transaction record are themselves vault-shaped (append-only, uniquely IDed) —
the evidence/ledger discipline applied to *distribution* rather than
conversation.

**Browser automation / Chrome master-slave.** The ship posture's execution
model — not a legacy trap, and not gated behind an AI-API pilot. The
correction from v1 is not "avoid Chrome"; it is *build Chrome as a declared,
capability-scoped realization (`provider.browser`) under CP-2's process tier,
badged and healed like anything else*, instead of a hardcoded singleton with
selectors as stored truth. It is also the healing loop's primary proving
ground — the realization guaranteed to drift. (The working set carries
`provider.browser` and the quarantined-realization framing; it does not carry
the ship-posture sentence — §4.10.)

**Canvas dev-poc and security hardening `vvv`.** The current canvas work is

exactly what CP-2's trust-tiered execution and the law gate are built to close;
they are inputs to the falsifiers, not separate work.

(AKB placement → §4.2, carried above.)
